# Interface localisation (BL-12)

Design spec, 2026-08-06.

## The problem

Every string the model shows is English and lives where it is used: the panel
markup in `index.html`, the module cards inside the geometry in `src/engine.js`,
the camera presets and the generated contrail sentence in `src/main.js`. There
is no way to show the model in another language, and no place to put one.

BL-12 in `docs/09-backlog.md` describes this task for Russian only. It also
states that "the wording for the second language already exists in the git
history". That is wrong: a scan of every commit reachable from every ref finds
no Cyrillic in any `.js` or `.html` file, including the initial commit. Every
translation is written from scratch. The backlog entry is rewritten as part of
this work.

## Scope

Eight locales: `en`, `ru`, `es`, `zh-Hans`, `fr`, `pt-BR`, `de`, `ja`.

`en` is the source language and the fallback. `fr` earns its place on merit
rather than reach — the prototype CFM56-7B is a GE/Safran engine and the French
side is the primary source behind half the reference data in `docs/engines/`.

Localised: all interface text, all module card prose, and number formatting.

Not localised: SI unit symbols (`°C`, `bar`, `kN`, `km`, `rpm`, `%`, `Pa`,
`kg/m³`). These are international designations, unchanged in aviation
documentation in every one of these languages. Translating them would make the
panel harder to read, not easier.

Out of scope, and deliberately so:

* `docs/` itself stays English. The written language of the repository is
  English by project convention; only the running application is localised.
* Imperial units. Aviation does live in feet and pounds of thrust, but a unit
  system is a separate axis from a language and belongs in its own task.
* `?lang=` in the query string. That is BL-10 (model state in the URL), and the
  language will join the rest of the state when BL-10 is done.

## Measured volume

| Source | Translatable text |
|---|---|
| `index.html` | 1263 characters — buttons, hints, section headers, gauge captions, legend, footer |
| `src/engine.js` | 2415 characters — 11 module titles and 398 words of card prose |
| `src/main.js` | ~1300 characters — 10 camera presets, `MODE_TEXT`, `VERDICT_TEXT`, `STATIONS` names, power-button labels and four hints, contrail sentence templates |

About 5 kB of text per locale, roughly 8 kB per file once keys are counted.
Eight locales add about 64 kB to the bundle and about 19 kB gzipped.

## Architecture

```
index.html (data-i18n) ──┐
                         ├→ main.js → i18n.js ← src/locales/{en,ru,es,zh-Hans,fr,pt-BR,de,ja}.js
engine.js (keys)      ───┘
```

`src/i18n.js` knows nothing about Three.js or the DOM, joining `engineState.js`,
`atmosphere.js`, `contrail.js` and `sound.js` on the headless side of the
project. This is not abstraction for its own sake: a headless browser renders
this scene at about 1 fps, so anything that must be tested has to run under
Node.

```js
createI18n({ locales, initial }) → { t, n, locale, setLocale, available }
pickLocale(preferred, available) → tag
```

* `t(key, params)` resolves against the active locale, falling back to `en` for
  a missing key.
* `n(value, digits)` formats a number through `Intl.NumberFormat(locale)`.
* `pickLocale` matches `navigator.languages` against the eight tags by
  descending specificity: `pt-PT → pt-BR`, `zh-TW`/`zh-HK` → `zh-Hans`,
  `de-AT → de`, `sv-SE → en`, empty → `en`. A pure function; no browser needed
  to test it.

Locales are plain ES-module objects, all bundled. Lazy loading through dynamic
`import()` was considered and rejected for now: it would save the ~19 kB gzipped
at the cost of an async boundary at start-up and a flash of untranslated text,
which is a bad trade at 8 kB per locale. If the teaching layer (BL-22) lands and
multiplies the text volume, the switch to `import()` is a change at the single
point where a locale is loaded — no `t()` call site moves.

## Keys, and unloading `engine.js`

`module(name, title, info, explode)` currently carries 2415 characters of
English prose through the middle of the geometry. The two text arguments are
dropped. Module names are already unique (`nacelle`, `fan`, `booster`, …), so
the keys follow from them: `module.nacelle.title`, `module.nacelle.info`. The
prose moves to `locales/en.js` and `engine.js` goes back to being about
geometry.

`userData.title` and `userData.info` are replaced by resolution at display time,
`t('module.' + g.name + '.title')`. This also fixes a case the current code
cannot handle: a card that is open when the language changes.

`geometry.test.mjs` and `clearance.test.mjs` build the real scene under Node but
never read module titles, so they are unaffected.

## Generated sentences

`refreshContrail()` in `src/main.js` assembles its explanation by concatenating
fragments:

```js
`The air is ${margin} °C below the threshold, so a trail forms; `
  + (persistent ? `it is supersaturated over ice… ${where}.` : …)
```

Concatenation cannot survive translation — word order differs across the eight
languages, and a fragment that reads correctly in English may have no
grammatical position in Japanese.

The `where` clause carries a second switch of its own: the verb is "stop" when a
trail currently forms and "start" when it does not (`src/main.js:565`). So there
are five `where` variants, not two.

The fragments are replaced by whole sentences keyed on the outcome:

```
trail.forms.persistent    {margin} {where}
trail.forms.shortLived    {margin} {where}
trail.none                {margin} {where}

where.higher.stop         {km}      used with trail.forms.*
where.lower.stop          {km}
where.higher.start        {km}      used with trail.none
where.lower.start         {km}
where.nowhere             —
```

Eight keys, and the one remaining seam falls on a **sentence boundary** — in the
English original `where` is already a separate sentence, ending the hint after a
full stop. Joining two complete sentences is safe in all eight languages in a
way that joining clauses is not. A translator is free to reorder anything inside
either sentence.

**No plural machinery, deliberately.** The only countable noun in generated text
is the distance in `where.higher` / `where.lower`, and it always prints with one
decimal place (`toFixed(1)`), which selects the same grammatical form in all
eight languages. Percentages and temperatures carry no noun. Blade and stage
counts appear only inside static card prose, where the translator writes the
sentence whole. There is nothing for plural rules to do.

## Switcher and persistence

A native `<select id="lang">` in the panel `<header>`. Options are endonyms —
`English`, `Русский`, `Español`, `中文`, `Français`, `Português`, `Deutsch`,
`日本語` — identical in every locale. There is nothing to translate, and a
reader looks for their own script rather than a translated language name. A
native select renders in the system font, so no font asset is needed and the
project's no-external-assets rule holds.

On a language change:

1. `applyStatic()` walks `[data-i18n]` and rewrites `textContent`.
2. The parts built once at start-up are refreshed explicitly: `refreshModeUI()`,
   `refreshContrail()`, the camera-preset buttons (`src/main.js:258-263`), the
   3D module labels (`src/main.js:85-92`), the open module card, the legend and
   the station-table header.
3. `document.documentElement.lang` is updated — CJK line breaking depends on it.

Persistence: `localStorage['turbofan.lang']`, written on change and read at boot
before the first render. Both access points are wrapped in `try`/`catch`:
`localStorage` throws in private mode and in a sandboxed iframe, and the model
must keep running without remembering the choice.

First visit with nothing stored: `pickLocale(navigator.languages, available)`.

Hotkeys are not localised. The letters stay bound to the English mnemonics
(`C` — cutaway, `S` — sound, `X` — x-ray, `E` — start/shutdown), only the
explanations in the footer are translated. Two reasons: `zh-Hans` and `ja` have
no letter to be mnemonic with, and a Russian keyboard layout reports different
`event.code` values for the same physical keys. Keeping one layout for everyone
also keeps muscle memory and screenshots portable between languages.

## Tests

An eighth file, `test/i18n.test.mjs`, in the style of the existing seven: a
plain Node script with its own `check()` helper, one `OK`/`FAIL` line per check,
exit code 1 on failure.

1. **Key parity.** Every locale has exactly the key set of `en` — none missing,
   none extra. This is the check that keeps eight translations from drifting
   apart, and the reason the whole dictionary is worth testing at all.
2. **Placeholder parity.** The set of `{…}` names in each template matches the
   English one. A translator who drops `{margin}` produces a sentence with a
   hole in it, and nothing else would catch that.
3. **`pickLocale`.** `ru-RU`, `pt-PT`, `zh-TW`, `de-AT`, `sv-SE`, empty input.
4. **No empty values.**
5. **Markup agrees with the dictionary.** Every `data-i18n` attribute in
   `index.html` names a key that exists in `en`. The file is read as text under
   Node and the attributes taken by regular expression. This catches the
   ordinary drift where markup is renamed and the dictionary is not.
6. **Number formatting.** `ru` and `de` produce a comma, `en` a dot.
